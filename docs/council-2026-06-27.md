## Состав совета

## Контекст
Оценивается система мониторинга проектов бюро (16+ сотрудников, 17 проектов):
GitHub Actions (каждые 30 мин + 9:00 МСК) → Google Sheets CSV → JSON снапшоты → GitHub Pages дашборд + Claude API отчёт.

---

## CTO
**Архитектура правильная, безопасность критически нарушена.**

- GitHub Actions + Pages корректно решают требование "независимо от ПК" ✅
- Публичный репозиторий + публичный лист = внутренние данные компании доступны любому ❌
- Нет retry-логики: один неудачный HTTP-запрос роняет весь workflow
- Race condition: два workflow одновременно делают `git push` без `git pull --rebase`
- XSS: данные из Google Sheets вставляются через `innerHTML` без экранирования
- Нет алертинга при сбое — система может молчать неделями
- Через год: ~17 500 коммитов и файлов в history/ — git checkout замедлится

**Приоритеты CTO:** закрыть репо → перенести дашборд на приватный хостинг → retry → concurrency lock → убрать `rows` из снапшотов

## CPO
**Дашборд показывает состояние, но не помогает принимать решения.**

- Закрывает базовую боль ("видеть картину без заходов в Sheets") — 6/10
- Отсутствует временная динамика: нет трендов "неделю назад было 3 просрочки, сейчас 7"
- Нет кросс-матрицы сотрудник × проект — без неё невозможно перераспределить нагрузку
- Бейдж `badge-overloaded` определён в CSS, но нигде не рендерится (баг в `index.html`)
- Блок "Изменения за 24 часа" зависит от AI-отчёта — если анализ не сформировался, блок пуст
- Нет push-механизма: дашборд ждёт, когда на него зайдут — руководитель перестанет заходить

**Приоритеты CPO:** Telegram-нотификация → тренды → кросс-матрица → "экран планёрки" → умный мэтчинг (потом)

## COO
**60–70% вероятность заброшенности в текущем виде.**

- Ценность односторонняя: сотрудники заполняют таблицу, получает только руководитель
- Если часть команды обновляет нерегулярно — аккуратные выглядят перегруженными, остальные свободными
- Алгоритм создаёт иллюзию контроля при некачественных данных — это опаснее отсутствия данных
- Нет "владельца" системы, который следит за её здоровьем

**Рекомендация по внедрению:**
1. Тихий запуск (2 нед.) — руководитель сам тестирует, сверяет с реальностью
2. Показать ценность на планёрке с конкретным примером
3. Одно простое правило: обновлять статус в день изменения — не больше

## Data Director
**Найдены критические баги, ломающие систему при реальных данных.**

| Баг | Эффект |
|---|---|
| `.decode("utf-8")` вместо `.decode("utf-8-sig")` | BOM-маркер → все проекты = пустая строка |
| `r.get("Задача", "")` без fallback в `detect_changes` | Если столбец "Задача/Роль" — ключи пустые, изменения не отслеживаются |
| Ключ = конкатенация без разделителя | Коллизии: "АнализИванов" ≠ "Анализ\|\|\|Иванов" |
| Нет `else` между overdue и blocked | Одна задача = два риска в списке |
| `json.loads()` без try/except | Если Claude вернёт markdown-блок — анализ не создастся |
| max_tokens=2000 | Длинный JSON обрежется на середине → crash |
| Нет system prompt для Claude | Нестабильное качество ответов |

**Вывод Data Director:** при реальном ручном заполнении ожидается 15–30% ошибок в аналитике.

---

## Консенсус (все 4 эксперта согласны)

1. **Архитектура правильная** — GitHub Actions + Pages верно решает задачу "независимо от ПК"
2. **Публичность = критический риск** — репо и данные должны быть закрыты немедленно
3. **Нужен алертинг** — без push-уведомлений система пассивна и будет заброшена
4. **Качество данных — главное узкое место** — система настолько хороша, насколько аккуратно заполняется таблица
5. **MVP работает, продакшен — нет** — концепция доказана, но до ежедневного использования нужны доработки
